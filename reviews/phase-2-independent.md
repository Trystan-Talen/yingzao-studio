## 1. 可直接采纳的决策

| 决策 | 独立意见 | 需要保留的边界 |
| --- | --- | --- |
| 统一TypeScript、严格类型、单pnpm工程 | 通过 | React只管UI；公开DTO来自contracts；服务端领域不能导入React/Fastify；禁止大型万能route/component |
| React/Vite登录工作台，Fastify同域托管 | 通过 | 开发代理与生产同域都明确；生产验收针对构建产物而非仅dev server |
| Fastify app工厂与listen入口分开 | 通过 | 路由仅鉴权/校验/调用用例；业务规则不得只存在于浏览器或某一个入口 |
| SQLite/Drizzle/better-sqlite3 | 通过 | API与worker短写事务；WAL、外键、busy timeout、迁移入口与恢复文档明确；不在DB事务中等待模型/媒体处理 |
| 独立worker与持久任务/事件 | 通过 | 租约、fencing token、幂等与不确定提交核对机制必须保持，不能简化成setTimeout+内存队列 |
| 本地私有媒体存储与资产变体 | 通过 | original/preview/thumbnail/export清楚分开；不能通过静态公开目录绕过workspace权限 |
| 服务端权限/账本/能力校验 | 通过 | 浏览器、开放API、worker使用相同service规则；请求不能自报角色、余额或成功结果 |
| SceneDocument revision与pendingApply | 通过 | 生成成功与应用成功分离；用户确认时再次检查revision；旧任务不能覆盖新项目 |
| 原生provider适配，按能力启用 | 通过 | 模型品牌名不当协议；连接成功不当全部能力成功；缺配置返回未就绪且不得扣额度 |
| 测试fake仅注入自动化测试 | 通过 | 产品默认环境不得假生成、假支付、假发票或用原站样图冒充用户产物 |
| 渐进依赖与明确版本 | 通过 | 安装前锁定版本兼容组合，提交lockfile；不引入未有具体用途的Redis、微服务或训练服务 |

原研究已清楚考虑第三方提交崩溃窗口、租约过期、重复回调、部分成功、账本幂等、资产来源、当前权限重检和备份恢复。这些是优点，不需要另造一套复杂框架替换。

## 2. 正式规格定稿前的6项门槛

### B01（P1）：范围如何转成可验收的产品能力

问题：52项覆盖台账是调查范围，尚不是可开发PRD。若只做菜单+通用表单，图片组合规则、视频四类复刻、多轮会话、画布原图与团队账本会遗漏；反过来，照静态接口无差别做所有旧功能又会错误膨胀范围。

建议：建立F编号→用户流程→本地能力/外部能力→权限→数据对象→API→验收用例的正式追踪表。每种创作/工具使用类型明确的输入schema，不把所有字段存为无校验JSON。F38旧品牌模板/订阅、F52活动及F34资料库等弱证据域必须有明确处置，不能被“全功能”一词掩盖。原站未观察的规则由新产品明确设计并注明来源。

关闭证据：有版本化PRD与覆盖表；图片/视频/工具、账户/团队/商业/开放API每个功能域有正常、错误、空态、权限和恢复用例。细化到具体工具可复用规则，但不得只写“与原站一样”。

### B02（P1）：本机媒体到远端provider的传输契约

问题：本机默认loopback与私有storage正确，但远端模型无法从用户传入的 `http://127.0.0.1/...` 读取素材。没有传输方案，参考图/视频/遮罩/音频等功能会在真正联调时整体失效。一个“可配baseUrl”不能解决这个问题。

建议：每个适配器声明输入传输类型（直接字节/multipart、base64、供应商上传后file ID、受限远程URL）。优先使用其真实支持的直接上传方式；只有确实要求远程URL的协议才依赖明确配置的可达资源地址/对象存储。不得自动公开本机、启动隧道或把所有私有资产变成公共文件。外部下载链接须限定资产、用途和有效期；获取供应商输出后落入自有存储。

关闭证据：至少一个图像和一个视频契约的媒体传递流程图/DTO，含输入大小限制、上传失败、返回链接过期、无公网地址时的错误；适配器不发明其供应商不存在的upload/submit/poll/cancel路径。真实凭据可以待配置，不影响文档关闭。

### B03（P1）：队列并发、取消与结算必须是一套状态协议

问题：草案已有强基础，但“HTTP入口检查并发”还不够。排队后实际开始运行的时刻必须原子占用workspace/provider并发名额；供应商取消仅被受理而未终止时，不应立即释放远端并发或把任务标成已取消。否则两个worker或重启恢复仍可能超额提交。

建议：把“接受排队”“占用执行名额”“请求取消”“已证实终态”分别定义。claim事务同步校验/占用执行名额；终态释放一次。对于有远端ID的运行任务，刷新、租约丢失或用户取消都不能再次submit；取消不支持时保持真实状态并说明结果可能仍产生。不确定提交保留 `reconcile_required`，不可一键重试成重复收费任务。

关闭证据：状态转换表、claim/heartbeat/terminal事务伪代码、唯一约束，以及同任务重复提交、两个worker抢任务、旧租约写入、取消与完成交错、成员移除后的回收/取回行为。事务和状态设计先审查，故障注入测试在实现阶段落实。

### B04（P1）：计价版本、额度预留和供应商成本分离

问题：原站按张、秒、分辨率、参考视频、图层等计费，不能统一“每任务1积分”。另一方面，未知输出图层/批量部分成功和供应商真实成本不能被随意回填成用户费用。

建议：生成请求固化pricing version、参数快照、预估量、最大可预留额、取消/失败/部分成功的结算策略。对外用户额度与内部供应商成本分别记录，收费规则是本产品规则，不由供应商错误消息或未经校验的返回字段决定。金额用整数最小货币单位；额度也用明确的整数基础单位，所有整数范围/换算/舍入有规定。队员预算建议作为团队余额上的独立预算约束，避免把团队余额与成员预算相加成双倍可用余额；若选择实际划拨则必须完整定义转入/转出。

关闭证据：至少给出普通图片、按秒视频、批量部分成功、取消已产生成本、重复回调五个结算例子；写明流水唯一业务键、余额可用计算、配额有效期与到期预留处理。没有商户密钥不妨碍账本设计与本地验证。

### B05（P1）：画布引擎、文档格式和导出一致性

问题：原研究定义了revision，但没有明确采用哪种编辑引擎以及导出时如何保留文字、字体、变换、裁剪、组合和真实原图。如果编辑器和导出器各自实现一套布局，就会产生“浏览器好看、下载错位”。

建议：优先评估 **Fabric.js 作为浏览器编辑交互层**，自有 `SceneDocument` 作为稳定业务文档；引擎序列化只是适配层，不直接作为不受控的数据库schema。对象ID、坐标原点、单位、字体、资源ID、裁剪和变换约定固定，版本迁移显式处理。视频图层保存媒体/时间数据，不用截图冒充视频导出。导出先确定支持格式和范围，再用同一文档与字体资产产生结果；不承诺未实现的SVG/PSD等格式。

官方文档确认Fabric提供对象交互、层叠顺序、视觉状态序列化及图像输出，但JSON不保存自定义控件/行为，SVG导入与导出也不保证一一对应。因此必须由应用恢复交互逻辑并检查实际导出。[Fabric核心概念](https://www.fabricjs.com/docs/core-concepts/)

另外7.x文档说明默认 `originX/originY` 改为 `center`。无论最终锁定哪个受支持版本，都应显式设置坐标约定，不能照搬原站旧序列化后假设位置一致。[Fabric 7迁移说明](https://www.fabricjs.com/docs/upgrading/upgrading-to-fabric-70/)

关闭证据：正式选择编辑引擎与固定版本策略；SceneDocument v1示例覆盖图片、文本、组、裁剪、视频及引用资产；编辑与导出共享规则说明；后续验收包含中文字形、透明度、旋转/缩放/裁剪、分组、跨分辨率导出与实际文件尺寸。库版本安装可在阶段4完成，但选择必须先明确。

### B06（P1）：首次启动、所有者与真实服务配置路径

问题：仅有认证、provider_configs和API Key表名不足以保证用户拿到源码后能进入系统、配置服务并验证全流程。若默认账户/密码写死、所有套餐满额、依赖手改DB或全部服务显示ready，都会破坏交付质量。

建议：定义幂等首次初始化流程、首个本地owner、用户自己的凭据设定、个人workspace、演示/初始赠送额度的明确来源流水、配置与健康页。不要预置可被误认为真实付款的订单。初版秘密优先由服务端环境文件配置，UI显示配置状态/能力清单；若支持UI写密钥，单独设计加密与主密钥恢复。模型未配置时本地资产、画布、团队和任务历史正常可用，依赖生成的按钮清楚说明缺少的能力且服务端拒绝收费任务。

关闭证据：从空目录/空库到可登录项目的运行手册，env schema及`.env.example`字段清单，owner/member的配置权限、健康状态、迁移/备份/恢复入口与首次使用流程；密钥不需要在评审时存在。

## 3. 应随架构文档固定的实施细节

这些是现有正确方向的具体化，不再单独增加调查门槛。

- **数据库约束**：job创建幂等键含workspace/调用方与请求hash；相同key不同payload返回冲突。job item结算、provider webhook事件、pending_apply、收藏及成员关系有唯一约束。工作区内关联写入逐一校验归属。
- **文件与DB一致性**：媒体下载/处理先临时写入、验证并原子发布；DB最终事务引用已就绪文件。发布后DB提交失败会留下可回收孤儿文件，要有延迟清理清单；软删除、品牌引用、画布历史、在途任务持有引用时不能立即删原文件。
- **SSE与事实源**：业务状态和持久事件在同一事务提交；实时通知只是加速。断线以有序ID恢复，失效游标返回snapshot/re-sync；鉴权检查在每个订阅。流式文本可以成批持久化，不必让每个字符独占SQLite写事务。
- **会话编排**：会话消息、可选方向、参数快照和生成任务引用有类型。模型输出不能作为任意系统命令或直接修改余额/角色/状态的授权；LLM只提出受schema约束的内容/工具建议，由服务端合法用例执行。
- **流程与provider分离**：`workflow`描述产品流程，`capability`描述技术能力，`model`/`provider`描述具体协议。允许图像翻译等由多步组合，但首版用显式的有限步骤处理器，不先建通用可编程工作流引擎。
- **功能状态**：区分configured、credential verified、contract tested、live tested、enabled。无真实密钥可完成代码/故障测试，但不能在UI或交付文档标live tested。
- **构建规范**：明确Node基线、ESM/TypeScript模块解析、API/worker输出路径和pnpm版本；客户端禁止打包服务端模块。原生依赖安装验证、`typecheck/lint/test/build`在实现阶段运行并留结果。
- **错误与日志**：统一稳定error code、用户可读message、request/job ID；原始provider错误和账户秘密只在经过脱敏的服务端上下文处理。禁用吞错后空数组/假成功响应。

## 4. 建议的架构定稿文档最小集合

1. `PRD.md` 与 `feature-coverage.md`：52域范围处置和核心用户流程、状态、验收映射。
2. `ARCHITECTURE.md`：已选技术、模块图、运行/存储边界、目录与依赖规则。
3. `DATA_MODEL.md`：ER关系、唯一约束、工作区范围、文档schema、媒体生命周期、数据迁移。
4. `API_CONTRACTS.md`：请求/响应/错误/认证/幂等/SSE约定，至少列明各域端点；可在实现后从同源schema生成OpenAPI。
5. `JOB_AND_CREDIT_STATES.md`：执行、重试、取消、不确定提交、价格/预留/结算、pendingApply。
6. `PROVIDERS.md`：逐能力传输/提交/查询/取消/认证的真实协议与缺配置行为，区分已文档核对和已真实联调。

可合并文件以减少重复，以上是内容要求，不要求为了形式制造六套重复定义。正式schema和实现完成后，文档指向同一来源，不分别维护互相矛盾的接口。
